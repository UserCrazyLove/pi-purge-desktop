# PI Purge — PI-Desktop 插件版

把 [pi-purge](https://github.com/ZiChuanLan/pi-purge)（pi CLI 扩展，v0.2.4）转成 PI-Desktop 插件，
并且额外带一个**可视化控制面板**：开关、组合模式、人设来源、本会话实际切除结果都能直接点。

> **适配并实测于 PI-Desktop v0.21.0**；版本下限 0.15.9（插件数据目录 API 的引入版本），更旧的宿主上两侧一起退到插件旁的 `state/`。

机制没有改：宿主身份句不是被压住，而是被**清掉**。

| 模式 | 送出的系统提示词 | 什么时候用 |
| --- | --- | --- |
| `strict`（默认） | 人设 + `Current working directory: …`，宿主提示词整段丢掉 | 想把「只有我的人设」当成唯一变量 |
| `replace` | 人设 + 宿主提示词，但切掉身份句与内置 pi 文档段 | 想量化框架影响，同时保留工具说明和项目上下文 |
| `append` | 人设 + 原样的宿主提示词 | 对照运行，改动最小 |

工具 schema 走 API 的 `tools` 参数，不在系统提示词里，所以三种模式下工具照旧可用。

## 与 pi CLI 版的差异

1. **多了控制面板**（`ui.panel`），不用记命令也能操作。
2. **状态跨会话保留**：面板写的 `enabled / mode / source` 存在状态目录里的 `config.json`，
   扩展在每次 `session_start` 和每一轮开始前读它。也就是说面板打开开关之后，
   **新会话默认也是开的**（CLI 版是每个会话都从关闭开始、且不落盘）。
   想完全回到 CLI 语义：删掉 `config.json`，或把开关关掉后删掉该文件。
3. **每一轮写状态目录里的 `status.json`**，面板据此显示「上一轮到底切掉了什么」。
4. 面板与 `/purge` 命令共用同一份状态：哪边后写就以哪边为准，不会互相打架；
   两边只改自己拥有的 `enabled / mode / source` 三个字段，其它字段原样保留。
5. **写盘是原子替换、配置损坏时面板拒绝保存**：详见下面的「状态目录与配置文件」一节。

## 结构

```
manifest.json                      插件清单（agent.extension + ui.panel）
main.cjs                           宿主侧入口：面板窗口、面板 RPC、状态文件读写
extensions/pi-purge.extension.mjs  Agent sidecar 侧的 pi 扩展：before_agent_start 改写 + /purge 命令
persona/embedded.md                内嵌示例人设（扩展与面板都读这一个文件，不存两份）
renderer/index.html                面板文档
renderer/panel.css                 面板样式（跟随宿主明暗主题）
renderer/panel.js                  面板逻辑（轮询状态、写配置、拖拽人设文件）
test/pi-purge.extension.test.mjs   扩展测试：模拟 ExtensionAPI + 真实宿主提示词形状
test/panel-host.test.mjs           宿主插件测试 + 面板 id 接线一致性检查
state/                             插件目录内的兜底状态目录（仅数据目录不可写时才用；正常情况状态文件在宿主数据目录，见「状态目录与配置文件」）
```

面板和扩展分处两个进程，它们只通过状态目录里的两个小 JSON 文件协商：
面板写配置，扩展读配置、写状态，面板再把状态画出来。没有 IPC、没有网络、没有共享内存。

## 状态目录与配置文件

状态目录是**三层候选**。面板侧（`main.cjs`）与扩展侧各自按**同一份候选列表、同一顺序**解析，
并且各自**做一次真实写入探测**（`mkdir` 后写一个带进程号 pid 后缀的 `.pi-purge-probe-<pid>` 探针文件，再删掉），
取第一个真的可写的目录：

| 顺序 | 候选目录 | 什么时候命中 |
| --- | --- | --- |
| 1 | 宿主给本插件的数据目录：`pi.plugin.getDataPath()`，默认布局 `<pi-desktop 数据目录>/plugins/data/local.pi-purge`（Windows 上通常是 `C:\Users\<你>\.pi-desktop\plugins\data\local.pi-purge`） | 正常可写的安装都落在这里。这个目录**不在插件目录里**，开发插件的递归文件监听看不到它 |
| 2 | `<插件目录>/state` | 只在数据目录不可写时使用。注意：开发插件用到这里就会触发重载循环，所以正常情况不会用到 |
| 3 | `<插件目录的上一层的上一层>/data/local.pi-purge` | 数据目录与 `state/` 都不可写时的最后兜底。真实安装布局是 `<plugins>/installed/<id>`，这一条正好是 `<plugins>/data/<id>` |

只读安装、数据目录不可写时两边**一起**退到同一个候选（不会一边一个）。探测结果会缓存，
开发插件被热重载时清掉重探。**面板底部会显示当前实际使用的状态目录**（`状态目录 <路径>`）；
候选都不可写时面板显示「状态目录不可用」并列出候选，而不是随便指一个没人在用的目录。

**特殊情况**：宿主把数据目录放在非默认位置（`pi.plugin.getDataPath()` 与上面的默认布局不同）时，
`main.cjs` 会在插件目录里留一个 `state-location.json` 记录真实路径 —— 只在内容真的不同时才写，
免得自己把自己触发一次重载；扩展优先读它。

配置文件本身的行为：

- 写盘是**原子替换**：先写 `${file}.tmp-<pid>`，再 `rename`，所以对面永远不会读到半截文件。
- `config.json` **存在但不是合法 JSON** 时，面板不会把默认值当真实状态显示然后覆盖它：
  面板显示「配置损坏」与具体错误，并且**拒绝保存**，直到用户修好或删掉那个文件。
  扩展侧遇到损坏文件会忽略它（当没有配置，走默认值：关闭 / `strict` / 内嵌）。
- 面板与命令**只写自己拥有的三个字段**（`enabled` / `mode` / `source`），
  文件里的其它字段原样保留；`updatedBy` 记录这一笔是面板还是命令写的。
- 面板里填的**相对路径会先被解析成绝对路径**再存盘，
  避免面板与扩展各自用自己的工作目录去解析同一个相对路径。

## 安装

两种方式，任选。两种方式的状态文件位置相同（见上一节）：

**A. 用打好的包（推荐）**

```bash
node pi-desktop-plugin/test/pi-purge.extension.test.mjs   # 可选：先自检
```
然后对插件目录跑 `PluginPack`（或已生成的 `dist/local.pi-purge-0.2.4.piplug`），
在 PI-Desktop 的**插件页 → 安装本地 .piplug** 选中它。安装时会提示授予
`agent.extension`（高风险）与 `ui.panel`。

**B. 直接把这个文件夹当开发插件载入**

在插件页选择「加载本地插件目录」并指向本目录。此目录会被宿主热重载：
改了 `renderer/*` 或扩展文件后保存即生效；**改 `permissions` 需要重新载入一次**
（避免热重载顺手提权）。
状态文件默认就写在宿主给本插件的数据目录里（见「状态目录与配置文件」一节），不在插件目录内；
那个数据目录也不可写时，面板与扩展会一起退到插件目录下的 `state/`，再退到 `<plugins>/data/<id>`，不会一边一个。

> 注意：在本仓库里直接跑 `PluginScaffold` 生成骨架的那次加载会失败，报
> `module is not defined in ES module scope` —— 因为仓库根 `package.json` 是
> `"type": "module"`，插件的 `main.js` 会被当成 ESM。这也是本插件的入口叫
> `main.cjs` 的原因（PI-Desktop 自己的 pi 扩展导入器同样写 `main.cjs`）。

## 使用

打开面板：命令面板里搜 **PI Purge**，运行「PI Purge: 打开控制面板」；
或先跑一次「PI Purge: 开/关当前会话」，之后从插件页的面板按钮进入。

面板上能做的事：

- **总开关**：开启 / 关闭。改动在**下一条消息**生效（扩展在每轮开始前读配置）。
  写入成功后立刻用返回值刷新界面，不等下一次轮询；每次写入都会让在飞的旧轮询响应作废，
  界面不会被旧状态画回去。
- **组合模式**：三张卡片直接切 `strict` / `replace` / `append`。
- **人设来源**：`内嵌示例`，或填一个路径（相对路径会先被解析成绝对路径再存盘）；
  也可以把 `.md` 文件**拖进面板**自动填路径。
  下面会显示字符数、行数与前 4000 字符预览，读不到文件会直接标红说明原因。
  预览最多只读 512 KB + 前 4000 字符，超过会标出来并警告「扩展仍会整份读进系统提示词」；
  文件带 BOM 或空字节（看起来不是 UTF-8）也会给出警告。只有大文件（> 64 KB）才按
  `mtime + size` 缓存；小文件每次轮询都重读，所以「同长度、同时间戳」的替换也不会被漏掉。
- **人设读不到不会把开关偷偷关掉**：`enabled` 保持你要的状态，只是这一轮不改写，
  `status.json` 里的 `loadError` 说明原因；**把文件修好即可，下一条消息自动生效，不需要重新开关**。
  但显式命令仍然会拒绝：`/purge on` 在正文读不到时报「无法开启」，
  `/purge source <坏路径>` 会回滚到上一个人设并且不写配置。
- **本会话实时状态**：会话开关、生效模式、生效人设、上一轮切除结果
  （身份段 / pi 文档段是否命中）、宿主提示词字符数 → 实际送出字符数、工作目录。
- **底部**：当前实际使用的状态目录（见「状态目录与配置文件」一节）。

两个容易踩的地方：

- 标签「**本地文件**」只是把焦点给路径输入框，本身**不写配置**：真正切到内嵌示例是点「内嵌示例」，
  真正切到本地文件是点「使用这个文件」（在输入框里回车也一样）。
  你正在路径框里输入时，轮询不会回填覆盖你的输入。
- 「**重新读取**」只刷新**预览**（提示语会写明「正文在下一轮生效」）；正文仍然在下一条消息生效。

命令（agent 侧，输入框直接打）：

| 命令 | 作用 |
| --- | --- |
| `/purge` | 开 / 关（切换） |
| `/purge on` · `/purge off` | 显式开启或关闭 |
| `/purge status` | 模式、人设、上一轮切除情况 |
| `/purge mode strict\|replace\|append` | 切换组合模式 |
| `/purge source <绝对路径\|embedded>` | 换人设文件，或回到内嵌示例；失败会回滚 |
| `/purge reload` | 改完人设文件后重新读取 |

`/purge` 的结果会写回状态目录里的 `config.json`，所以面板立刻就能看到。

## 权限与副作用

- `agent.extension`（高风险）：扩展在 Agent sidecar 里运行，并改写本会话外发的系统提示词。
- `ui.panel`（低风险）：宿主给面板窗口。
- **不联网**：插件不发任何请求，`net` 权限一个都没申请。
- 文件读写只发生在两处：插件的状态目录（首选项是宿主给本插件的数据目录 `<pi-desktop>/plugins/data/local.pi-purge`；不可写时退到 `<插件目录>/state`，再退到 `<plugins>/data/<id>`），
  以及**你自己在面板里填的那一个人设文件**（只读）。
  人设文件通过 `main.cjs` 的 Node 侧读取，路径是你显式给的；插件不会去扫描目录。
- 关闭状态下扩展**不读**人设文件：只在开关开启、或正文还没加载过时才真正去读。

## 已知限制

- `strict` 会连同 `AGENTS.md` / 项目上下文、技能清单、其他扩展注入的提示词一起丢掉 —— 这正是它干净的代价，
  也意味着 `strict` 下的结果不能和普通会话直接比较（与 CLI 版一致）。
- 配置是**全局一份**（状态目录里的 `config.json`），不是每会话一份。多个会话同时开着时，
  面板的开关对所有会话生效。
- 面板显示的是**最近一次运行的会话**写下的状态；如果同时开了多个会话，
  面板上的「本会话」指的是最后跑过一轮的那个。
- 面板通过每 1.5 秒轮询 `purge.state` 取状态；宿主没有提供插件向自己面板推送事件的方式。
- 人设改动在**下一条消息**生效，不会改写已经发出的请求。
- 配置损坏时面板只能显示错误与原因，不能替你修；修好或删掉那个文件之后面板恢复正常读写，
  在此之前面板拒绝保存，避免把默认值当真实状态写回去。
- 面板里的 4000 字符预览**只是预览**，不是扩展实际读入的正文：超长或非 UTF-8 的人设文件，
  扩展仍然会整份按 UTF-8 读进系统提示词。
- **状态文件绝不能放在插件目录里**：开发插件目录是被宿主**递归监听**的，把状态写进插件目录（`state/`）会被当成源码变更 → 宿主热重载插件 → 重载又重新探测并写状态 → 重载风暴（实测约 5 次/秒）。这正是候选列表把宿主给的数据目录排第一的原因。

## 开发与验证

```bash
 node pi-desktop-plugin/test/pi-purge.extension.test.mjs   # 15 项：三种模式、配置接管、人设读不到不关开关、失败回滚、损坏配置、状态写在插件目录之外（防重载循环）、state-location.json 指针、只读兜底、相对路径绝对化、锚点失配退化
 node pi-desktop-plugin/test/panel-host.test.mjs           # 12 项：命令注册、面板 RPC、相对路径绝对化、损坏配置、数据目录不可用时的兜底、超长预览、预览不被同长度同时间戳的改动骗过、插件目录零写入、指针文件、面板 id 接线
npm test                                                  # 上面两项 + 原 CLI 版的两套
```

扩展测试用的提示词形状取自 PI-Desktop 宿主自己的模板：同一句
`You are an expert coding assistant operating inside pi, a coding agent harness.`、
同一段 `Pi documentation (read only when the user asks about pi itself…`，
以及 `(e.g., tui.md for TUI API details)` 结尾 —— 也就是 `stripHostPersona` 依赖的两个锚点。
锚点失配时（比如宿主改了文案）行为退化为 append，测试里专门覆盖了这一条。

面板测试会核对 `panel.js` 里 `getElementById` 用到的每个 id 都真的存在于 `index.html`，
以及文档确实加载了面板脚本、样式和 `pi-plugin-chrome` 标记 —— 面板最容易错的就是这种接线。
